# Ticketing UI re-audit — 1.0.25

Date: 2026-10-21. Revision: `9ca4edb0b3e0b218a0e584a306bfba87072dde74`.

Disposition: **UI acceptance is not ready. Regular requesters have lost the visible ticket-creation entry point.** This is a read-only audit, not an implementation or deployment. The audit did not change application source, production accounts, databases, SQL, or the release version. Publication at the user's request adds this documentation and generated JSON evidence only.

## What this audit covers

“Full ticket service with the UI” includes the three queue variants, ticket details, escalation history/actions, creation, comments/internal notes, attachments/previews/replacement, status changes, cancellation/duplicates, record/time corrections, satisfaction forms and public invitations, Knowledge Base, ticket reports/performance, ticket settings, duties, attendance, staff directory, ticket-facing dashboard, profile/settings, manuals, and shared navigation/notification/dialog/theme boundaries. Compliance-document, issuance, incident, KPI, and other non-ticketing workflows are not part of this re-audit.

The source inventory resolves 15 UI entrypoints and their local imports: **66 files / 28,539 lines**, including API/types/helpers and the route/CSS boundaries. It inventories 55 Dialog declarations, 186 Button declarations, 60 IconButton declarations, 198 TextField declarations, 20 Autocomplete declarations, 29 Table declarations, nine Tabs declarations, and eight TicketImageDropzone consumers. These are source occurrences, not counts of unique runtime states or a claim of line-by-line semantic certification.

Every ticketing UI owner was included in source inspection and control/dialog enumeration. Runtime validation is deliberately recorded separately: **85 exercised local browser probes**, with some probes walking several tabs or dialogs. Two incorrectly named/unavailable correction probes were replaced by explicit correction-dialog checks. The assigned-ticket fixture's incomplete mark-viewed response and the original one-person reassignment fixture were corrected and rechecked; their earlier exceptions/timeouts are not application defects. The validated evidence has no unresolved probe execution failure, remaining fixture page exception, or source-hash mismatch. “Exercised” does not mean the UI passed—the probes reproduced the defects below.

## Findings

The 29 entries below are confirmed implementation/UI-baseline gaps, not 28 security vulnerabilities. Runtime reproduction and source-only evidence are distinguished. P1 means a blocked workflow or materially unsafe interaction; P2 means misleading state, lost work, or significant usability/accessibility inconsistency; P3 means a lower-risk clarity/polish gap. The current profile does not establish a formal accessibility conformance target, so this report makes no WCAG certification claim.

## Polish recommendations / candidate standards, not additional confirmed defects

1. **Compact mobile support selection:** four roughly 170px cards consume most of a small dialog before Subject/Description. Use a compact accessible selector or progressive detail; the fields are scroll-reachable, not missing. See mobile creation: local-only screenshot `create-mobile.png`.
2. **Named density variants:** create/filter actions currently range through roughly 31/37/44/56px depending on page/container. Define compact/default/touch variants with a reason. Do not mechanically make every button equal size or every action primary.
3. **Shared terminology and titles:** Requestor/Requester/Requested For and technician/staff/assignee need deliberate scope definitions. Dialog titles such as “Add reservation” expose an internal entity name while the page says Meeting Schedule. The requester/filer distinction must remain intact.
4. **Risk-specific confirmations:** settings removal text should name the selected category/issue/focal, dependencies and consequence rather than “this category.” The duplicate pre-confirmation's “Yes, Continue” is less precise than its eventual Confirm Duplicate action. Required confirmation must not be inferred solely from red styling.
5. **Information hierarchy:** dense timing explanations, long report headings and repeated full-form satisfaction markup warrant shared layouts and progressive disclosure; keep pause-count/estimate explanations available. Do not simplify away audit/SLA facts.
6. **Live freshness and service availability:** preserve the already-good offline/notification retry behavior, and extend deliberate last-updated/stale feedback where losing live transport would materially affect an operational decision. Physical native safe areas, virtual keyboards and actual installed bundle behavior need runtime acceptance, not assumptions from CSS.

## Recommended fix order and validation

1. Restore requester creation. Re-test the actual regular-user workflow from navigation through confirmed creation, including pending satisfaction behavior and server ownership rules.
2. Add pending/dismissal protection and correct the feedback pagination contract. Verify exactly one UI request and correct pages/totals under delayed/failed responses.
3. Fix false empty/not-found/success feedback and embedded search freshness. Exercise first load, stale refresh, denied/missing, server failure, out-of-order and retry.
4. Fix keyboard/control naming for selectors, calendars, ratings, browse and preview; retain focus and the same permitted actions.
5. Standardize responsive action layout, labels/required fields, dark surfaces and temporal formatting using shared scoped components/variants—not blanket style replacements.
6. Run builds/types and focused regression tests after implementation, then repeat the affected role/status matrix, mobile/dark/keyboard/zoom checks, source diff and screenshot review. Changes to shared components require consumer review. Native devices, real uploads, print/PDF and production data need separately controlled acceptance.
