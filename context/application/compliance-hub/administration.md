# Administration and Capability Overlay

## Guidelines and structure

Capability definitions and grants -> backend route checks -> record/unit policies -> frontend discoverability. Staff-directory identities, pending identities, and active accounts are separate states.

## Rules

- CH-ADMIN-001 MUST define new privileged actions through the existing capability model where applicable.
- CH-ADMIN-002 MUST enforce backend checks even when the UI hides the action.
- CH-ADMIN-003 MUST preserve resource ownership and unit scope beyond a broad capability check.
- CH-ADMIN-004 MUST update capability storage/bootstrap, checker/decorator use, frontend type/admin controls, and tests together when adding a capability.
- CH-ADMIN-005 MUST treat staff-directory failure as an explicit failure state; do not silently remove already valid active accounts.
- CH-ADMIN-006 MUST avoid granting privileges based on a display role label alone.
- CH-ADMIN-007 MUST restrict changes to the application-wide idle screen-lock duration to Security Settings capability holders. Store whole minutes from 1 to 1440 (one day) with a 15-minute default; zero does not disable locking. Authenticated clients receive only the duration through the session-policy projection. Measure idle time from user activity, never from heartbeat or policy refreshes; applying a changed duration must preserve the last-activity time and must not unlock an already locked session. This setting controls the existing client screen lock, not token expiry or server-session revocation.
- CH-ADMIN-008 MUST recover a valid existing session only within protected application routes. Login, MFA, public pages and explicit sign-out must not silently restore an account. Temporary network/service failures preserve credentials and previously verified state; initial access remains blocked until profile and capabilities are verified. Retry only session reads with capped backoff and at most one renewal per failed request, sharing renewal across concurrent callers and serializing browser-cookie rotation across tabs where supported. Definitive expiry/revocation/account rejection still requires sign-in. Explicit sign-out must cancel pending recovery and remain effective during an outage; only successful interactive sign-in/MFA clears that intent. Preserve idle locks during recovery and wait for API readiness before a new-build page reload.
- CH-ADMIN-010 MUST expose Unlock MFA only within existing account-management authority: limited managers recover regular accounts; account administrators cannot recover other administrators without role-management authority; only another Super Administrator may recover a Super Administrator. Deny self-recovery and inactive actors/targets. Recheck persisted actor/target state in the transaction; ticket-administration authority alone is insufficient. Require an identity-verification acknowledgement, a trimmed 10–500 character reason and an opaque current-state precondition. Clear the current OTP, failure counters, lock, prior MFA verification proof and trusted-device exemptions; preserve password, role, account activation, units, existing sessions and the MFA requirement. An explicit actor/target/reason audit must commit with the unlock or the operation rolls back. Completed retries are no-ops; changed recovery state requires review rather than clearing a newer challenge. Registering a trusted device must check the current successful verification proof under the same account lock so an earlier request cannot restore an exemption after recovery.
- CH-ADMIN-011 MUST serialize OTP issuance, consumption, failed-attempt accounting and administrative recovery on the account row. Preserve three wrong entries per login and nine accumulated failures before a 15-minute lock. Requesting another code does not erase accumulated failures; expiry of that lock starts a fresh attempt allowance when issuing another code. Correct verification consumes once and resets failure state. Password and Google sign-in both respect an active MFA lock and return an OTP challenge, withholding full session credentials until verification when application MFA is required. Invalidated/expired OTPs return the owner to fresh sign-in without claiming that MFA was disabled. A Google screen-unlock challenge must match the currently locked account and retain the screen lock until successful verification.

## Implementation

Login MFA under CH-ADMIN-011 uses two independent settings: Temporary MFA Mode on requires a challenge and displays its code in the application without emailing it. With temporary mode off, enabled outbound email requires an emailed challenge and never returns the code to the browser. Both off skips the challenge. The authoritative outbound flag includes Global Settings and the system-wide email kill switch; SMTP or policy outages must not be interpreted as a disabled setting. Preserve existing trusted-device expiry checks and the explicit VAPT bypass. Password and Google sign-in share this decision. Clear stale temporary codes when entering email mode and remove temporary-code alerts when leaving verification. Email OTP destination selection and unit exemptions remain CH-ADMIN-013. Verify all combinations, denied/unavailable/malformed policy, email publish failure, lockouts, verification, and trusted-device expiry; full session credentials must remain withheld until required verification succeeds.

- CH-ADMIN-012 MUST restrict manual UMS unit synchronization to account-administration capability holders and reuse the existing active-work-history source and unit restrictions. The action applies to existing active accounts matched by Staff ID, independent of list filters; it does not enable automatic scheduling, create accounts or run the separate staff-directory import. Preserve manual assignments until the current assignment and UMS agree. Recheck active identity, target-unit classification and overrides under the account lock before changing units. Commit each unit/override change with an actor-context audit and notify affected clients. Show updated/new/retained/skipped counts; overlapping runs and source failures must not appear as successful zero-change runs. Individual accounts may commit before a later failure, so an unknown/failed result requires list refresh and deliberate retry.

Manual unit-sync journey: User Management → Sync Units from UMS → confirm scope → protected POST → ticket-snapshot readiness check → fresh source read → per-account validation/audit → result counts and refreshed list. `UMS_UNIT_SYNC_ENABLED` governs automatic runs; an explicit administrator action uses the configured UMS connection on demand. Connection details remain server-side. Verify manual and matching overrides, ambiguous active work histories, inactive/missing users and units, changed role/unit restrictions, unavailable UMS, overlapping submission and audit rollback. Unit changes must not rewrite existing ticket data, assignment, status, routing, access or SLA. The ticket requester-unit display follows CH-TICKET-018; sync refuses to run while ticket baselines are missing. Future outbound delivery uses the recipient's current unit under CH-ADMIN-013, independently of the ticket's historical snapshot.

- CH-ADMIN-013 MUST restrict changes to the outbound-email unit policy and its unit-options projection to Security Settings capability holders. Default the restriction off without changing existing SMTP/master controls. When enabled, an empty selection blocks all routine email; otherwise a unique active recipient account must currently belong to an active selected unit. Unknown recipients, missing/inactive/unselected units and unavailable policy suppress routine delivery. Evaluate at actual dispatch, including cron notifications, manual feedback invitations and SMTP tests; manual-invitation bypass of the general notification toggle does not bypass unit policy. If a routine email uses a test override, both original recipient and destination must pass the policy. Only trusted producers may classify OTP/recovery as security messages: these bypass unit and general routine-notification restrictions, honor the configured Test Override Email for authentication/recovery and feedback verification codes (including an override outside selected units), and still respect the system-wide `EMAIL_ENABLED` kill switch. Do not infer exemptions from subjects or caller-provided UI fields. Log only safe suppression reasons/account references, never codes, links, subjects, mailbox values or content. Report blocked feedback invitations as skipped, preserve existing links on preflight rejection, and revoke a newly created link if sending is suppressed after preflight. Do not change in-app notifications, feedback access, ticket records, SLA or assignment. Suppressed messages are not automatically replayed when units are enabled later.

Outbound policy journey: Security Settings capability → toggle + searchable unit selection → validated/audited Users config → private service-authenticated recipient decision → shared SMTP dispatch → sent/suppressed/failed outcome. Preserve selections while the restriction is off; confirm an enabled empty selection. Display inactive/unavailable saved units rather than silently discarding them; reject unknown/new inactive selections at save. Each send reads current account/unit state, so a transfer affects future delivery, never ticket history. Unit options are a dedicated Security Settings projection, not a grant to Units Management. Verify save/reload, empty/off states, permissions, unknown units, recipient transfers, policy outage, SMTP tests/overrides, OTP exemptions, invitation suppression and unchanged in-app feedback. Clearing the test override immediately restores security mail to its original recipient. Controlled manual invitation links retain their selected recipients when general notifications are off; their verification codes still honor the override. This test-routing revision supersedes the original no-OTP-redirection rule by the owner’s explicit 2026-11-04 correction. Verify override present/absent/cleared with routine notifications on and off; OTP must not be duplicated to the original recipient. Candidate portable pattern: purpose-aware recipient policy at the shared delivery boundary.

- CH-ADMIN-009 MUST accept an authenticated account's unchanged, format-valid Staff ID during profile/password-reset completion without requiring a successful external-list lookup. Resolve that account ID from server authentication, never caller-supplied ownership. Changed nonempty Staff IDs retain approved-list validation and duplicate-account protection; enforce self-update validation at the backend as well as the UI. Do not rewrite saved identity, bypass password policy or infer that a different person's ID belongs to the caller. Directory failures must not invalidate an already established unchanged identity (CH-ADMIN-005).

Update detection under CH-ADMIN-008 uses a public static manifest containing only version/build identity. Check every two minutes only while visible, and on focus/online/visibility return. Omit cookies on manifest requests, bound valid build IDs, preserve the in-flight/reload-loop guards and wait for API readiness before refreshing protected app pages. This is frontend update detection, not session renewal or an account-data endpoint.

Connection recovery under CH-ADMIN-008 bounds profile, capability and live-event ticket reads to 15 seconds including interceptor waits. Cookie renewal has a 30-second total bound including cross-tab lock acquisition; logout aborts that wait. Manual Retry can cancel a stalled attempt and only the current attempt may restore state. SSE uses the existing 20-second server heartbeat with a 75-second visible-tab watchdog and fresh-ticket reconnects; hidden tabs defer stale-stream polling, and returning to a visible tab reconciles missed changes. A cookie-only renewal is not a sign-out.

Unlock MFA inputs and consumers: management-list metadata supplies only a recovery-needed flag, lock expiry and HMAC-protected recovery version (no code, password or raw counters). The dialog collects owner-identity confirmation and the reason; the protected endpoint validates these plus the current version against the locked account. Validation/conflict errors retain the dialog inputs, and Refresh/reopen obtains a current version. The essential journey is User Management → locked account → confirmation/reason → audited unlock → owner signs in for a fresh OTP → verification succeeds. Check insufficient capability, stale state, failed audit, duplicate submission, cooldown expiry and concurrent OTP/recovery.

[RequireCapability](../../../backend/src/common/decorators/require-capability.decorator.ts) declares coarse requirements; [CapabilityGuard](../../../backend/src/common/guards/capability.guard.ts) evaluates known checkers. Its array requirement currently means any matching capability, not all. Services still need record-level predicates. [Frontend auth types](../../../frontend/src/lib/types/auth.ts) support UI visibility.

## Validation

Test no session, missing/unknown capability, changed grants, record scope, pending directory identity, unavailable directory, and direct endpoint access. Do not infer that all endpoints already use the same authorization scheme.
